# pynteracta v0.4.0 — Tasks read (M17)

> **Status: PLANNED.** Spec for the next minor. Read-only, additive. No change to existing flows.
> Follows the conventions of the [foundation spec](v0.1-foundation.md), the
> [posts read-completeness spec](v0.2-read-surface.md) and the
> [attachments spec](v0.3-attachments.md), and the patterns logged in
> [`PROGRESS.md`](../PROGRESS.md) (M5 resource clients, M9 communities/catalogs, M15 posts read,
> M16 attachments). Index: [`ROADMAP.md`](../ROADMAP.md).

## 1. Objective

Expose the **tasks read surface** of the Interacta API as a new first-class resource. After
v0.3.0 added attachments, v0.4.0 adds the single read endpoint that fetches a task's full detail
by id. A task belongs to a post (`postId`) and carries assignment, workflow state, sub-tasks,
reminders, watchers and survey data.

Targets a **minor bump 0.3.0 → 0.4.0** via a `feat:` commit. Service-account and Google OAuth2
flows unchanged; all existing resource clients unchanged. This introduces a **new resource group**
(`tasks`) rather than extending an existing API.

## 2. Endpoints in scope

All paths under `{base}/api/external/v2/`.

| # | Method | Path | Request DTO | Response DTO | Notes |
|---|---|---|---|---|---|
| 1 | GET | `communication/tasks/data/task-detail-by-id/{taskId}` | – | `GetTaskDetailResponseDTO` | Single task detail. Rich shape: `id`, `postId`, `title`, `descriptionDelta`/`descriptionPlainText`, `expiration`, `priority`, `state`, `currentWorkflowState`, `assigneeUser`/`assigneeGroup`, `reminders` (`TaskReminderDTO`), `subTasks` (`SubTaskDTO`), `creator`/`lastModify`/`lastReview`/`closing` audit users + timestamps, `timeToReview`/`timeToClosed`, `mentions`, `watcherUsers`/`watcherGroups`, `hashtags`, `occToken`, `type`, `attachmentsCount`, `surveyData` + `surveyDataCommentsInfo`, `capabilities` (`TaskCapabilitiesDTO`). New facade `Task`. |

> **Codegen check (Q5 pattern):** confirm whether `GetTaskDetailResponseDTO` (or any nested DTO)
> generates as a `RootModel[Any]` stub with a typed `…Model`/`…1` sibling (as happened in
> M3/M5/M9/M15/M16). The facade and API layer must bind to the typed variant. The pinned
> `tests/fixtures/swagger.json` already contains the task DTOs — no regeneration needed unless a
> field is missing from `src/pynteracta/models/generated/external_v2.py`.

> **Out-of-scope siblings (do not implement):** `POST communication/tasks/manage/create-task/{postId}`,
> `PUT communication/tasks/manage/edit-task/{taskId}/{occToken}` and
> `DELETE communication/tasks/manage/delete-task/{taskId}` are **write/manage** endpoints — deferred
> to the future write line. The response's `occToken` is the propaedeutic edit token for those.

## 3. Deliverables

- **`models/facade/tasks.py`** (new module) — `Task` facade (composition over
  `GetTaskDetailResponseDTO`) with `extra="ignore"` and `.raw` escape hatch. Surface the curated
  core (`id`, `post_id`, `title`, `description_plain_text`, `expiration`, `priority`, `state`,
  `current_workflow_state`, `assignee_user`/`assignee_group`, `attachments_count`,
  `creation_timestamp`, `creator_user`) and expose the richer nested structures
  (`sub_tasks`, `reminders`, `watcher_users`/`watcher_groups`, `survey_data`, `capabilities`)
  via properties / thin sub-facades as warranted — keep the same composition style used for
  `Post`/`PostAttachment`. Per **D-v0.4-4**: curate `description_plain_text` (mirroring the `Post`
  facade); leave `descriptionDelta` (Quill rich-text JSON) and the survey payloads
  (`surveyData`, `surveyDataCommentsInfo`) to `.raw`.
- **`api/tasks.py`** (new module) — `TasksAPI(ResourceClient)`:
  - `get(task_id: int) -> Task`
  - Follow the established "one method, one shape" convention; use the `_utils` query/body builders.
    (No `*_raw` variant needed — the endpoint takes no request body; a single path param.)
- **`client.py`** — register `self.tasks = TasksAPI(...)` on `InteractaClient`.
- **`cli/tasks.py`** (new Typer sub-app) — wired through `render_output` (so `--output`, `--full`,
  `--fields`, `--export` all compose). Registered on the top-level CLI:
  - `tasks get <taskId>`
  - `--web-url` behaviour per **D-v0.4-3** (deep-links to the parent post, since a task carries
    `postId`).
- **Models** — re-export the new facade(s) from `models/facade/__init__.py` and
  `models/__init__.py` (and their `__all__`).

## 5. Resolved decisions

- **D-v0.4-1 — resource grouping.** *Resolved:* introduce a dedicated `TasksAPI` / `tasks` CLI
  group rather than folding the endpoint into `PostsAPI`, even though a task belongs to a post.
  Mirrors the M16 decision to give attachments their own group.
- **D-v0.4-3 — `--web-url` target.** *Resolved:* **include** `--web-url` on `tasks get`, deep-linking
  to the **parent post** via the task's `postId` and `WebUrls` (the canonical web view for a task is
  its post). This differs from the attachments group (D-v0.3-3b), where a bare attachment had no
  `postId` to anchor on. If the post community is needed to build the URL, source it from the task
  payload / an extra lookup at implementation time (see Q-v0.4-2).
- **D-v0.4-4 — facade depth for survey/description.** *Resolved:* curate **`descriptionPlainText`**
  onto `Task.description_plain_text`, exactly mirroring the `Post` facade. Leave **`descriptionDelta`**
  (Quill rich-text JSON-as-string) and the survey payloads (**`surveyData`**,
  **`surveyDataCommentsInfo`**) to `.raw`. Rationale: the established convention curates only scalar
  fields and routes rich-text deltas + complex nested structures through the `.raw` escape hatch
  (CLAUDE.md: "Facade `.raw` is intentional"). Decisively, swagger types `surveyData` as an
  **untyped `object → object` map** (no DTO), so there is no clean shape to wrap — `.raw` is the only
  faithful surface. `surveyDataCommentsInfo` maps to `SurveyDataCommentsInfoDTO` but is a niche
  survey-comment structure, also deferred to `.raw`. The curated CLI table therefore shows
  `descriptionPlainText` (truncated) and never the delta/survey blobs.

## 6. Open questions

- **Q-v0.4-2 — `--web-url` inputs.** Confirm at implementation/integration time whether
  `WebUrls` can build the post deep-link from `postId` alone or also needs the community id (and, if
  so, whether it is present on the task payload or requires a follow-up `posts.get`).
- **Q-v0.4-3 — `currentWorkflowState` vs `state`.** Inspect both fields on a real payload to decide
  which the curated CLI table shows (task lifecycle `state` vs post workflow state) and document the
  distinction in the CLI help.

## 7. Out of scope

- **Write/manage tasks:** `create-task`, `edit-task`, `delete-task` — deferred to the future write
  line (see [`ROADMAP.md`](../ROADMAP.md)). The read response's `occToken` is carried through `.raw`
  for future write use but no write method is added here.
- Any mutation. Groups & hashtags (0.5.0), admin manage edits (0.6.0) — their own later minors.
