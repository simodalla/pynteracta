# pynteracta v0.9.4 — PyPI publication (M26)

> **Status: ⏳ Planned.** Infrastructure release: no new read surface, no new endpoint group, no
> change to `src/`. Brings forward the PyPI publication that
> [`ROADMAP.md`](../ROADMAP.md) and [`WORKFLOW.md`](../WORKFLOW.md) had deferred to 1.0, and
> documents the discontinuity with the pre-existing `pynteracta` line on PyPI.
> Follows the conventions of the [foundation spec](v0.1-foundation.md) and the
> [v0.9.2 GitHub-migration spec](v0.9.2-github-migration.md) (M24), whose release plumbing this
> release extends. Index: [`ROADMAP.md`](../ROADMAP.md).

## 1. Objective

Until now every distribution channel has been GitHub-only: `release.yml` attaches a wheel and an
sdist to a GitHub Release on each `v*` tag, and the documented install path is
`uv pip install "pynteracta @ git+https://github.com/simodalla/pynteracta@vX.Y.Z"`. The project
policy (`ROADMAP.md` §Versioning policy, `WORKFLOW.md` §2) deferred PyPI publication to 1.0.

This release brings that publication forward, on the decision taken 2026-09-12
(**D-v0.9.4-1**), and adds the publishing job to the existing release workflow.

**The distinguishing fact of this release** is that the PyPI project `pynteracta` already exists
and is owned by the same author. It carries 30 releases up to **0.4.30** (last of the old line),
published under **BSD-3-Clause**, wrapping the Interacta API with an entirely different — and
incompatible — public API. The current codebase is a from-scratch rewrite. Verified differences
against the published `0.4.30` wheel: modules `api.py` / `core.py` / `models.py` / `schemas/` /
`settings.py` replaced by the `InteractaClient` façade over `api/` resource clients; the console
script renamed from **`pynta`** to `pynteracta`; `requests` replaced by `httpx`; BSD-3-Clause
replaced by Apache-2.0; the write surface dropped (read-only for now). Both lines already require
Python >= 3.12, so that is *not* a differentiator despite the old release's stale
`Programming Language :: Python :: 3.10/3.11` classifiers.

Publishing `0.9.3` onto that project therefore means a consumer on `pynteracta==0.4.x` who runs
`pip install -U pynteracta` receives a library whose API does not match their code, from a version
number that looks like an ordinary minor step. The old releases are deliberately **left in place**
(**D-v0.9.4-2**): no yanking, no deletion, so existing pins keep resolving. The discontinuity is
handled by documentation instead — a compatibility note in `README.md`, which is the PyPI project
description and therefore the first thing such a consumer sees.

Targets a **patch bump 0.9.3 → 0.9.4**: the deliverables are `ci:` and `docs:` commits with no
`feat:`, so `python-semantic-release` computes a patch (**D-v0.9.4-4**). **0.9.4 is itself the
first version published to PyPI** (**D-v0.9.4-3**).

## 2. Endpoints in scope

No endpoints. `src/pynteracta/` is not modified by this release. Files touched:
`.github/workflows/release.yml`, `pyproject.toml`, `README.md`, `ROADMAP.md`, `WORKFLOW.md`,
`docs/index.md`, `docs/quickstart.md`, `docs/development-workflow.md`, `PROGRESS.md`.

> **Out of scope:** any API-layer, CLI or model change; the deferred write surface; any change to
> the version-numbering policy (1.0 remains tied to read-surface completeness, see
> **D-v0.9.4-5**); any modification or removal of the 0.1.3–0.4.30 releases already on PyPI.

## 3. Deliverables

### D1 — PyPI publishing job (`.github/workflows/release.yml`)

- Split the existing single `release` job into two, so a PyPI failure cannot leave the GitHub
  Release half-created and vice versa:
  - `build` — checkout, `uv sync --frozen`, `uv build`, upload `dist/` as an artifact.
  - `github-release` — needs `build`, attaches the artifact to the GitHub Release (unchanged
    behaviour, `softprops/action-gh-release@v2`, `generate_release_notes: true`).
  - `pypi` — needs `build`, publishes with `pypa/gh-action-pypi-publish@release/v1`.
- **Trusted publishing (OIDC), no API token** (**D-v0.9.4-6**): the `pypi` job declares
  `permissions: id-token: write` and carries `environment: pypi`. No `PYPI_API_TOKEN` secret is
  added to the repository.
- Building once and publishing the same artifact to both destinations guarantees the wheel on PyPI
  is byte-identical to the one on the GitHub Release.

### D2 — README compatibility note (`README.md`)

Add a final section, after `## License`, stating explicitly:

- that the rewrite line (`0.9.3` in the repository, **`0.9.4` as the first PyPI upload**) is a
  **complete rewrite**;
- that the public API is **not compatible** with the `0.4.x` line and there is no migration path;
- that `0.4.30` remains installable via an explicit pin (`pynteracta==0.4.30`) for anyone on the
  old line, and that those releases are not being removed;
- that the old line was BSD-3-Clause and the rewrite is Apache-2.0;
- that the console script is renamed `pynta` → `pynteracta`, so the old command disappears on
  upgrade (the single most visible breakage for CLI users).

This section is the PyPI project description's landing content for upgraders, so it must be
self-contained — no reliance on repository-relative context.

### D3 — README/​docs install-path update

## 4. Resolved decisions

- **D-v0.9.4-1 — publish now, not at 1.0.** Decided 2026-09-12, superseding the deferral recorded
  in `ROADMAP.md` and `WORKFLOW.md`. The read surface is broad enough to be useful to install, and
  the GitHub-only install path (`git+https://…`) is friction for consumers and unusable from a
  plain `requirements.txt` in restricted environments. Deferring publication was a convenience
  choice, not a stability guarantee; the stability guarantee stays attached to 1.0.
- **D-v0.9.4-2 — the 0.1.3–0.4.30 releases stay on PyPI, unyanked.** Removing them breaks every
  existing `pynteracta==0.4.x` pin, and yanking them would push resolvers of unpinned old consumers
  onto the incompatible rewrite — the opposite of the intent. Leaving them in place means the old
  line keeps working exactly as it does today, and the discontinuity is communicated in prose
  (D2) rather than enforced by removal. PyPI never permits reusing a deleted version number, so
  this decision is also the reversible one.
- **D-v0.9.4-3 — the first published version is 0.9.4, this release (revised 2026-09-12).** The
  spec originally planned to publish the already-tagged `0.9.3` artifact first. That tag has
  already been pushed, so `release.yml` will not re-run for it without an artificial re-trigger,
  and the new `pypi` job did not exist when it ran. Publishing `0.9.4` instead means the first
  upload is produced by the very workflow being introduced, on a tag pushed after the job exists —
  no manual re-trigger, no divergence between what CI built and what PyPI receives. Since
  `git diff v0.9.3 main -- src/` is empty, `0.9.4` ships identical library code anyway, so nothing
  of substance is lost by skipping `0.9.3` on PyPI. `0.9.3` remains available as a GitHub Release.
  Consequence: PyPI's version history for the rewrite starts at `0.9.4`, with a gap after `0.4.30`.
- **D-v0.9.4-4 — patch, not minor.** No `feat:` commits: the deliverables are CI plumbing and
  documentation. Nothing in `src/` changes, so the installed library is byte-identical in
  behaviour to 0.9.3.
- **D-v0.9.4-5 — publishing to PyPI does not accelerate 1.0.** The versioning policy is unchanged:
  pre-1.0 lenient semver, `major_on_zero = false`, one read-endpoint group per minor, and 1.0 still
  gated on read-surface completeness plus a period of API stability. Being installable from PyPI
  and being API-stable are separate claims; `Development Status :: 3 - Alpha` carries the second.
- **D-v0.9.4-6 — trusted publishing, not an API token.** OIDC exchange means no long-lived secret
  is stored in the repository, nothing to rotate, and the publish is scoped to this repository's
  `release.yml` running in the `pypi` environment. This is the current PyPI-recommended mechanism
  and it removes the main standing credential risk of publishing from CI — consistent with the
  token-handling posture established in v0.9.3 (M25).
- **D-v0.9.4-7 — README links become absolute.** The same file serves as the GitHub landing page
  and the PyPI project description. Relative links work only in the former; absolute ones work in
  both. Pointing them at `blob/main` (rather than at a tag) keeps them valid across releases.
- **D-v0.9.4-8 — keep `Development Status :: 3 - Alpha`.** The classifier describes API stability,
  not distribution channel. Raising it to Beta on the strength of being published would overstate
  the guarantee, given the read surface is still incomplete and the write surface is untouched.
- **D-v0.9.4-9 — `upload_to_pypi` stays `false`.** semantic-release computes versions and cuts
  tags; distribution is the release workflow's responsibility, triggered by the tag it pushes. One
  publisher, one place to look when a publish fails, and no duplicate upload attempt.

## 5. Open questions

- **Q-v0.9.4-1 — should the rewrite eventually take a different PyPI name?** Reusing the name means
  the two incompatible lines share one project page and one version sequence forever. A separate
  name would be cleaner but splits discoverability and abandons the existing name's history. Left
  as-is for now; the README note (D2) is the mitigation. Revisit only if upgrade confusion is
  actually reported.
- **Q-v0.9.4-2 — is a `0.4.31` "sunset" release of the old line warranted?** A final 0.4.x release
  whose only change is a deprecation warning pointing at the rewrite would reach existing users
  through their normal upgrade path. It requires resurrecting the old codebase to build it, which
  may cost more than it returns. Not planned.
- **Q-v0.9.4-3 — should TestPyPI be wired in as a dry-run target?** A `workflow_dispatch` path
  publishing to TestPyPI would let the pipeline be exercised without consuming a real version
  number. Deferred: the first real publish (D-v0.9.4-3) already validates the job, and TestPyPI
  needs its own trusted-publisher registration.

## 6. Out of scope

- Any change to `src/pynteracta/` — this release must not alter installed behaviour.
- Yanking, deleting or otherwise modifying the 0.1.3–0.4.30 releases (**D-v0.9.4-2**).
- A migration guide from the `0.4.x` API: the rewrite shares no surface with it, so there is no
  mapping to document beyond the incompatibility statement itself (D2).
- Any change to the versioning policy or to the 1.0 criteria (**D-v0.9.4-5**).
- Publishing to TestPyPI (**Q-v0.9.4-3**), and signing/attestation of artifacts beyond what
  `pypa/gh-action-pypi-publish` provides by default.
