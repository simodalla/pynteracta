# pynteracta v0.7.0 — Posts filter & sort completeness (M20)

> **Status: PLANNING — ⏳ In progress.** Spec for the next minor. Read-only, additive. No change to existing flows.
> Follows the conventions of the [foundation spec](v0.1-foundation.md), the
> [groups & hashtags spec](v0.5-groups-hashtags.md), and the patterns logged in
> [`PROGRESS.md`](../PROGRESS.md) (M5 resource clients, M15 posts read completeness).
> Paired with the follow-up [users filter & sort spec](v0.8-users-filter-sort.md) (M21).
> Index: [`ROADMAP.md`](../ROADMAP.md).

## 1. Objective

Complete the **filtering and ordering** surface of the community post list endpoint
(`ListCommunityPostsFilteredRequestDTO`), turning today's opaque `**filters` passthrough into an
**explicit, validated, discoverable** API (typed kwargs + CLI options), while keeping `**filters`
as the documented escape hatch.

This minor adds **no new endpoint**: it deepens `list/community/{communityId}`, already shipped in
v0.1.0. The sibling work for the users list (`admin/data/users`) is split into a dedicated minor
v0.8.0 (M21) to honour the one-group-per-minor cadence.

Custom-field filters (`postFieldFilters` / `screenFieldFilters`) are made first-class: their fields,
allowed enum values, and types are **discoverable and (opt-in) validatable** against the community
**post-definition** — already exposed in v0.1.0 via `communities.post_definition(community_id)` —
plus a label/externalId builder so callers can express filters without memorising numeric ids.

Targets a **minor bump 0.6.0 → 0.7.0** via a `feat:` commit. Existing call sites keep working: new
kwargs are all optional, `**filters` passthrough is preserved.

## 2. Endpoints in scope

All paths under `{base}/api/external/v2/`. The endpoint already exists — this minor only expands
its parameter surface.

| # | Method | Path | Request DTO | Response DTO |
|---|---|---|---|---|
| 1 | POST | `communication/posts/data/list/community/{communityId}` | `ListCommunityPostsFilteredRequestDTO` | `PagedListPostsResponseDTO` (→ `PostList`) |

**Codegen stub → typed mapping** (the request DTO references `RootModel[Any]` stubs; bind facades
to the typed siblings — same pattern as M18):

- `ListCommunityPostsFilteredRequestDTO` (line 3598) carries top-level `orderBy` (str),
  `orderDesc` (bool), `pinnedFirst` (bool), plus `communityPostFilters` and
  `communityAttachmentFilters` typed as the **stubs** `CommunityPostFiltersDTO` (line 1198,
  `RootModel[Any]`) / `CommunityAttachmentFiltersDTOModel` (line 1190, `RootModel[Any]`).
- **Typed sibling `CommunityPostFiltersDTOModel` (line 3468)** is the real shape — bind here. ~30
  fields, the relevant ones: `title`, `description`, `containsText`, `createdByUserIds: list[int]`,
  `createdByGroupIds: list[int]`, `creationTimestampFrom/To: int`, `modifiedTimestampFrom/To: int`,
  `hashtagIds: list[int]`, `hashtagsLogicalAnd: bool`, `postTypes: list[int]` (1=CUSTOM, 2=EVENTO,
  3=QUESTIONARIO), `currentWorkflowStatusIds: list[int]`, `visibility: int`, `followedByMe`,
  `mentioned`, `toManage`, `onlyPinned`, `postFieldFilters`, `screenFieldFilters`, plus deferred
  long-tail (`eventPostFilter`, `acknowledgeTaskFilter`, `draftType`, `postSurveyTypes`,
  `toManageProcesses/StandardTasks`, `includeStatelessPosts`, `postId`, deprecated
  `createdByUserId`/`modifiedByUserId`).
- **Custom-field filtering** = `postFieldFilters: list[CustomFieldFilterDTO]` and
  `screenFieldFilters: list[CustomFieldFilterDTO]`. Typed sibling **`CustomFieldFilterDTO`
  (line 814)**: `columnId: int`, `typeId: int`, `parameters: list[...]`. `typeId` semantics
  (documented in the DTO): **1=EQUAL, 2=INTERVAL, 3=LIKE, 4=IN, 5=CONTAINS, 6=IS_NULL_OR_IN,
  7=IS_EMPTY**. Confirmed against a real production payload, e.g.
  `{"columnId":1411,"parameters":[226],"typeId":4}` (Q-v0.7-1 resolved).
- **Custom-field discovery/validation source — already shipped.** Each `columnId` corresponds to a
  field in the community **post-definition**, already exposed in v0.1.0 via
  `communities.post_definition(community_id)` → `PostDefinition.field_definitions`
  (`PostFieldDefinitionDTO1`: `id`, `type` (typed `FieldType` enum), `label`, `externalId`,
  `enumValues`, `validations`). **No new endpoint** — but the `PostFieldDefinition` facade currently
  **omits `enumValues`** (typed `PostFieldConfigEnumValueDTO`, line 664: `id`, `label`,
  `externalId`, `parentIds`, `deleted`), which this minor adds so callers can discover/validate the
  allowed parameter ids.
- **Field `type` → filter `typeId` mapping** (confirmed from production payloads, partially inferred
  for the rest):
  - `ENUM (7)`, `ENUM_LIST (8)`, `HIERARCHICAL_ENUM (13)`, `GENERIC_ENTITY_LIST (15)` → `IN (4)`,
    `parameters` = enum/entity ids (confirmed: 1411/7, 1908/8, 1415/15).
  - `DATE (4)`, `DATETIME (5)` → `INTERVAL (2)`, `parameters` = epoch-millis `[from, to]`
    (confirmed: 1954/5).
  - `STRING (6)`, `TEXT_AREA (9)`, `DELTA_AREA (11)` → `LIKE (3)`, `parameters` = `[string]`
    (confirmed: 1957/11).
  - `FLAG (10)`, `INT/BIGINT/DECIMAL (1–3)`, `FEEDBACK (12)`, `LINK (14)` → **to confirm** (Q-v0.7-4).
- `orderBy` allowed static values (from the DTO field description): `postCustomId`, `postTitle`,
  `postCreatorUser`, `postCreationTimestamp`, `postLastModifyUser`, `postLastModifyTimestamp`,
  `postLastModifyAndCommentTimestamp`, `postViewedByMeTimestamp`, `postModifiedByMeTimestamp`,
  `postCommentedByMeTimestamp`, `postScheduledPublication`, `postRecency`, **plus** the dynamic
  `postCustomField-{id}` form (order by a custom field — distinct from `postFieldFilters`).

> **Out of scope:** the other post list endpoints (`global-stream`,
> `community-list/{communityId}`); `communityAttachmentFilters` (attachment-side filtering, kept as
> passthrough/escape hatch); the long-tail `communityPostFilters` fields listed above.

## 3. Deliverables

### Library — posts (`api/posts.py`)
- Add **ordering** kwargs to `list_in_community` (forwarded through `iterate_in_community`):
  - `order_by: str | None` — validated client-side (fail-fast) against `POST_ORDER_FIELDS` plus the
    dynamic `postCustomField-{id}` form.
  - `order_desc: bool | None` (→ `orderDesc`), `pinned_first: bool | None` (→ `pinnedFirst`).
- Add a **curated subset of `communityPostFilters` fields** as explicit kwargs, assembled into a
  typed `CommunityPostFiltersDTOModel`:
  `title`, `description`, `contains_text`, `created_by_user_ids`, `created_by_group_ids`,
  `creation_timestamp_from`, `creation_timestamp_to`, `modified_timestamp_from`,
  `modified_timestamp_to`, `hashtag_ids`, `hashtags_logical_and`, `post_types`,
  `current_workflow_status_ids`, `visibility`, `followed_by_me`, `mentioned`, `to_manage`,
  `only_pinned`, `post_field_filters`, `screen_field_filters`.
- **Custom-field filter mechanism**: `post_field_filters` / `screen_field_filters` accept a list of
  `CustomFieldFilterDTO` (or dicts coerced into it) — each `{column_id, type_id, parameters}`.
  Provide a small `PostFieldFilter` facade / builder over `CustomFieldFilterDTO` with a
  `FilterType` enum/constant for `typeId` (EQUAL=1 … IS_EMPTY=7) for discoverability.

### Custom-field discovery, validation & builder (post-definition backed)
- **Surface `enum_values` on `PostFieldDefinition`** (`models/facade/communities.py`) — typed list
  over `PostFieldConfigEnumValueDTO` (`id`, `label`, `external_id`, `deleted`). Fills the current
  facade gap; required for both discovery and validation.
- **Opt-in validation** — `list_in_community` gains an optional `validate_with: PostDefinition | None`
  (and a standalone `validate_field_filters(filters, post_definition)` helper). When supplied, it
  checks, fail-fast with a clear `InteractaError` subclass: (a) each `column_id` exists in
  `field_definitions`; (b) for enum-typed fields, every `parameters` id is a known (optionally
  non-deleted) `enumValues.id`; (c) the field `type` ↔ filter `type_id` pairing is allowed per the
  mapping above. No validation when `validate_with` is omitted (default) — zero extra network calls.
- **Label/externalId builder** — a helper (e.g. `PostFieldFilterBuilder(post_definition)` /
  `build_field_filter(...)`) that resolves human inputs to ids using the post-definition:
  field `externalId` **or** `label` → `columnId`, enum `label` → enum `id`, and a sensible default
  `type_id` from the field `type` (overridable). Lets callers express
  `Tipologia in ["Altro"]` without knowing numeric ids.
- Long-tail `communityPostFilters` fields and `communityAttachmentFilters` stay reachable via the
  preserved `**filters` passthrough; `community_post_filters=` may also accept a pre-built
  `CommunityPostFiltersDTOModel` / dict as an escape hatch.
- New constant/`Literal` **`POST_ORDER_FIELDS`** + validator.
- `*_raw` variant unchanged (already accepts a pre-built request DTO).

### Shared helpers (`api/_utils.py`)
- **Date coercion helper**: accept `int` (epoch-millis), `datetime`, or ISO-8601 `str` for the
  `*_timestamp_from/to` kwargs, normalizing to epoch-millis before building the DTO. (Introduced
  here; reused by v0.8.0 for the user date filters.)
- Reuse existing `snake_to_camel` for `--filter key=value` key conversion (CLI).

### CLI (`cli/posts.py`)
- `posts list`: add `--order-by`, `--desc/--asc`, `--pinned-first/--no-pinned-first`; common filter

## 4. Resolved decisions

- **D-v0.7-1 — split from users.** Posts and users filter completion are two separate minors
  (0.7.0 posts, 0.8.0 users) to honour the one-group-per-minor cadence.
- **D-v0.7-2 — curated subset + passthrough.** Explicit typed kwargs for the common
  `communityPostFilters` fields + ordering; `**filters` and an optional pre-built
  `community_post_filters` remain the documented escape hatch for the long tail.
- **D-v0.7-3 — filters are typed, not best-effort.** The earlier "opaque payload" assumption is
  **withdrawn**: `communityPostFilters` binds to the typed sibling `CommunityPostFiltersDTOModel`
  and custom-field filters to `CustomFieldFilterDTO`. We build a properly typed request.
- **D-v0.7-4 — `--filter` keys are snake_case.** Converted via `snake_to_camel`, consistent with
  the explicit kwargs.
- **D-v0.7-5 — `order_by` validated client-side.** Fail-fast against `POST_ORDER_FIELDS` + the
  dynamic `postCustomField-{id}` form.
- **D-v0.7-6 — date filters accept int + datetime/ISO.** Coerced to epoch-millis; plain `int`
  passes through unchanged. (Helper lives in `api/_utils.py`, reused by v0.8.0.)
- **D-v0.7-7 — custom-field validation is opt-in.** Validation against the community post-definition
  runs only when the caller passes `validate_with=`; default is no validation and no extra network
  call. The post-definition endpoint is already shipped (v0.1.0) — no new endpoint added.
- **D-v0.7-8 — surface `enum_values`.** `PostFieldDefinition` gains `enum_values` (typed over
  `PostFieldConfigEnumValueDTO`), filling the current facade gap; prerequisite for discovery,
  validation, and the label builder.
- **D-v0.7-9 — label/externalId builder.** Provide a post-definition-backed builder that resolves
  field `externalId`/`label` → `columnId`, enum `label` → enum `id`, and a default `type_id` from
  the field `type`. Filters can also still be built directly by numeric id.
- **D-v0.7-10 — documentation is extensive and example-driven.** This surface ships a dedicated,
  worked-example guide (`docs/guides/filtering-posts.md`) plus CLI docs, full API-reference
  docstrings with examples, and a README/quickstart snippet — not just a changelog line. Examples
  mirror the real test fixtures. See the Documentation deliverable in §3.

## 5. Open questions

- **Q-v0.7-1 — custom-field filter payload shape. RESOLVED.** Custom-field filtering is
  `communityPostFilters.postFieldFilters: list[CustomFieldFilterDTO]` (and `screenFieldFilters`),
  each `{columnId, typeId, parameters}`, with `typeId` 1=EQUAL…7=IS_EMPTY. Confirmed from a real
  production payload (`{"columnId":1411,"parameters":[226],"typeId":4}`). The `postCustomField-{id}`
  form applies only to `orderBy`, not to filtering.
- **Q-v0.7-2 — `CustomFieldFilterDTO.parameters` element type. RESOLVED.** Generated as
  `list[dict[str, Any]]` but that is a swagger/contract inaccuracy: real payloads use a list of
  **heterogeneous scalars** whose shape depends on `typeId` — e.g. `IN (4)` → id list `[226]`,
  `INTERVAL (2)` → 2 epoch-millis bounds `[1780264800000, 1780955999999]`, `LIKE (3)` → string
  `["aaa"]`. Facade type: **`list[int | str | float]`** (effectively `list[Any]`), passed through
  unchanged, with per-`typeId` usage documented. The date-coercion helper is **not** auto-applied to
  `INTERVAL` bounds — callers supply the epoch-millis pair directly (kept simple).
- **Q-v0.7-3 — `--filter` / `--field-filter` value typing on CLI. RESOLVED.** Per-type explicit
  coercion, no global heuristic:
  - **`--field-filter COLUMN:TYPE:VAL[,VAL]`** — each `parameters` token is coerced
    deterministically: a token matching an integer literal (`^-?\d+$`) → `int`, otherwise `str`.
    This yields `[226]` (IN), `[1780264800000, 1780955999999]` (INTERVAL), `["aaa"]` (LIKE) exactly
    as the real payloads. `COLUMN` and `TYPE` are always parsed as `int`.
  - **`--filter key=value`** — **string-only** passthrough (no coercion). Fields needing
    `int`/`bool`/`list` are reached via the dedicated typed flags (`--visibility`, `--post-type`
    repeatable, `--created-by` repeatable, `--followed-by-me`, …), not via `--filter`.
  - Keep this rule consistent in v0.8.0 (Q-v0.8-3): `--filter` string-only there too.
- **Q-v0.7-4 — field `type` ↔ filter `typeId` matrix. RESOLVED (permissive).** `validate_with`
  enforces **only the confirmed pairings**: ENUM/ENUM_LIST/HIERARCHICAL_ENUM/GENERIC_ENTITY_LIST→IN,
  DATE/DATETIME→INTERVAL, STRING/TEXT_AREA/DELTA_AREA→LIKE (mismatch on these → error). For all other
  field types (FLAG, INT/BIGINT/DECIMAL, FEEDBACK, LINK) the type↔typeId check is **skipped, not
  rejected** — the server decides — to avoid false positives on unobserved combinations. The matrix
  can be tightened later as real payloads for those types surface.
- **Q-v0.7-5 — label-resolution ambiguity in the builder. RESOLVED.** `enumValues` can contain
  duplicate labels and `deleted: true` entries (e.g. "Progetto"/"Scuola" deleted in the sample).
  Builder semantics: match by exact `label`; **exclude `deleted: true` by default** (opt-in
  `include_deleted=True` to include); **raise on ambiguous/duplicate labels** asking the caller to use
  the id; `externalId` (when present) is the unambiguous key and is **preferred over `label`**. The
  same rules apply to field-label → `columnId` resolution (labels can also collide with field names).
