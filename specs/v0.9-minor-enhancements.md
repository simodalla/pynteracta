# pynteracta v0.9.0 — Minor enhancements grab-bag (M22)

> **Status: SHIPPED — v0.9.0 (2026-09-11). Frozen. Do not edit.** Collection minor for small, additive CLI/library
> enhancements. Read-only, additive. No change to existing flows.
> Follows the conventions of the [foundation spec](v0.1-foundation.md), the
> [posts filter & sort spec](v0.7-posts-filter-sort.md) (M20) and the
> [users filter & sort spec](v0.8-users-filter-sort.md) (M21), and the patterns logged in
> [`PROGRESS.md`](../PROGRESS.md) (M5 resource clients, M20 post field filters).
> Index: [`ROADMAP.md`](../ROADMAP.md).

## 1. Objective

Bundle a set of **small, independent enhancements** that round out the existing read surface without
introducing a new endpoint group. Unlike the one-group-per-minor line (0.2–0.6), this minor is a
deliberate **grab-bag**: each feature is self-contained, additive, and individually small enough not
to warrant its own minor (see **D-v0.9-1**).

Feature 1 surfaces `screenFieldFilters` (already supported by the posts API layer) through the CLI
as `--screen-field-filter`, symmetric to the existing `--field-filter`. Features 2–13 were promoted
on 2026-09-11 from a census of API-vs-CLI gaps, open follow-ups and doc gaps (see **Q-v0.9-1**).
They fall into four groups: **A** API→CLI parity, **B** validation & consistency, **C** CLI
ergonomics, **D** documentation.

Targets a **minor bump 0.8.0 → 0.9.0** via `feat:` commit(s). Every feature is optional and
backward-compatible; existing call sites and flows are unchanged.

## 3. Deliverables

### Feature 1 — `posts list --screen-field-filter` (confirmed)

- **CLI (`cli/posts.py`)** — add a repeatable `--screen-field-filter` option to `posts_list` with
  the same `COLUMN_ID:TYPE_ID:VAL[,VAL...]` grammar as `--field-filter`. Reuse the existing
  `_parse_field_filter` parser. Pass the parsed list to the existing
  `screen_field_filters=` kwarg of `client.posts.list_in_community` /
  `iterate_in_community` (no API-layer change required).
- **Tests** — unit (Typer runner) covering: parse + forward of `--screen-field-filter`,
  combination with `--field-filter`, and error path on malformed grammar.
- **Docs** — extend the `posts list` examples in `docs/cli.md` and the posts CLI help text.

### Group A — API→CLI parity

#### Feature 2 — `posts list`: remaining curated kwargs as flags

- **CLI (`cli/posts.py`)** — add `--description TEXT`, `--created-by-group INT` (repeatable),
  `--modified-from` / `--modified-to` (ISO-8601 or epoch-ms, same coercion as `--created-*`),
  `--hashtags-and/--no-hashtags-and`, `--visibility INT`, `--mentioned/--no-mentioned`. Each maps
  1:1 onto the existing `list_in_community` / `iterate_in_community` kwargs (`description`,
  `created_by_group_ids`, `modified_timestamp_from/to`, `hashtags_logical_and`, `visibility`,
  `mentioned`). No API change.
- **Tests** — unit (Typer runner): every flag lands on the right `communityPostFilters` key.
- **Docs** — `docs/cli.md` flag table + examples; the `posts list` docstring example that used
  `--filter mentioned=true` switches to the typed flag.

#### Feature 3 — `users list --last-access-from/--last-access-to`

- **CLI (`cli/users.py`)** — two options forwarded to `last_access_timestamp_from/to`
  (M21 kwargs, `to_epoch_millis` coercion happens in the API layer).
- **Tests** — flag lands on `lastAccessTimestampFrom/To` as epoch-ms.
- **Docs** — `docs/cli.md` users flag table.

#### Feature 4 — `groups list --status / --workspace / --web-url`

- **CLI (`cli/groups.py`)** — `--status INT` (repeatable → `status_filter`), `--workspace INT`
  (repeatable → `workspace_ids`), `--web-url` (uses the existing `WebUrls.group`, same
  `_curated`/`_extra` closure pattern as `users list`).
- **Tests** — body keys `statusFilter` / `workspaceIds`; `web_url` column present only when asked.
- **Docs** — `docs/cli.md` groups section.

### Group B — validation & consistency

#### Feature 5 — `posts list --validate` (resolves Q-v0.9-2)

- **CLI (`cli/posts.py`)** — opt-in flag. When set and at least one `--field-filter` /
  `--screen-field-filter` is given, perform one
  `client.communities.post_definition(community)` lookup and forward it as `validate_with=`.
  A failing validation raises `ValidationError`, already mapped to `EXIT_VALIDATION` (6) by
  `handle_error`. Without filters the flag is a no-op (no extra call).
- **Tests** — extra GET on the post-definition path is issued only with `--validate`; an
  unknown column id exits 6; a valid filter passes through unchanged.
- **Docs** — `docs/cli.md` + cross-link from `docs/guides/filtering-posts.md` §Opt-in validation.

#### Feature 6 — typed tokens in `--filter KEY=VALUE`

- **CLI (`cli/_common.py`)** — new shared `parse_kv_filters(values, *, option="--filter")`
  helper used by `posts list`, `users list` and (Feature 9) `catalogs entries`. Value coercion:
  `true`/`false` (case-insensitive) → `bool`, integer literal → `int`, otherwise `str`. Keys go
  through `snake_to_camel` as today. Malformed pairs exit 1 with the flag name in the message.
- **Tests** — coercion table (bool/int/str), snake→camel, malformed pair; both commands.
- **Docs** — `docs/cli.md`: drop the "values are always `str`" wording in the two passthrough
  paragraphs; describe the coercion rule.

#### Feature 7 — `EpochMs` in `groups get` and `tasks get`

- **CLI (`cli/groups.py`, `cli/tasks.py`)** — wrap `creation_timestamp` in `EpochMs` in the
  curated row, as `cli/posts.py` already does (introduced in `f41b02e`). JSON output is unchanged
  (`EpochMs` is an `int`); table output shows a UTC datetime string.
- **Tests** — table snapshots for `groups get` / `tasks get` regenerated and reviewed; JSON
  snapshots must not change.

### Group C — CLI ergonomics

#### Feature 8 — root `--version` / `-V`

- **CLI (`cli/__init__.py`)** — eager, `is_eager=True` callback option printing
  `pynteracta <__version__>` and exiting 0.
- **Tests** — output contains the version string; exit 0 without any sub-command.
- **Docs** — `docs/cli.md` global options block.

#### Feature 9 — `catalogs entries --filter KEY=VALUE` — **DROPPED at implementation**

- Verified on 2026-09-11: `ListPostDefinitionCatalogEntriesRequestDTO` has no scalar fields beyond
  the ones already exposed (`label`, `orderBy`, `orderDesc`, paging); the only extra is the nested
  `context` DTO. Pydantic would silently drop any other key, so a generic passthrough flag would be
  a no-op that *looks* like it works. Not shipped (see **D-v0.9-6**).
- `groups list`, `hashtags list`, `attachments list` were already excluded: their API methods have
  no `**filters` escape hatch and `groups list` uses `--filter` for the full-text filter.

#### Feature 10 — `--count` on `posts list` and `users list`

- **CLI** — when set, the command requests `calculate_total_items_count=True` with
  `page_size=1`, prints **only** the integer `total_items_count` on stdout and exits 0. Rendering
  flags (`--output`, `--full`, `--fields`, `--export`, `--web-url`) are ignored; combining with
  `--all` exits 2 (`EXIT_CONFIG`). All filter flags still apply, so the number is "matching
  items", not "all items".
- **Tests** — body carries `calculateTotalItemsCount: true`; stdout is exactly the number;
  `--count --all` exits 2.
- **Docs** — `docs/cli.md`.

#### Feature 11 — `--page-token TOKEN` on `posts list` and `users list`

- **CLI** — forwards the opaque token to `page_token=`. After a single-page call, if the
  response carries a `next_page_token` and `--quiet` is not set, print
  `Next page token: <token>` on **stderr** so stdout stays machine-parseable. Combining with
  `--all` exits 2 (`EXIT_CONFIG`).
- **Tests** — token lands in the body as `pageToken`; next token appears on stderr only when
  present; `--page-token --all` exits 2.
- **Docs** — `docs/cli.md` pagination note under both commands.

## 4. Resolved decisions

- **D-v0.9-1 — grab-bag minor.** This version intentionally bundles several small, independent
  enhancements rather than a single read-endpoint group. The one-group-per-minor cadence applied to
  the 0.2–0.6 read-completion line, which finished at 0.8.0; post-completion polish is collected
  here.
- **D-v0.9-2 — `--screen-field-filter` mirrors `--field-filter`.** Identical
  `COLUMN_ID:TYPE_ID:VAL[,VAL...]` grammar, same parser, same numeric-token coercion. Keeps the two
  filter families symmetric and discoverable.
- **D-v0.9-3 — no API-layer change for Feature 1.** `screen_field_filters` already exists end-to-end
  in `api/posts.py`; the work is purely CLI surfacing + tests + docs.
- **D-v0.9-4 — `--count` is a print-only mode.** It emits just the integer total and ignores rendering
  flags, rather than adding a footer or a field to the normal output. Keeps `--output json` shapes
  stable and makes the number trivially scriptable (`$(pynteracta users list --count)`).
- **D-v0.9-5 — next-page token goes to stderr.** `--page-token` surfaces the follow-up token on
  stderr, never in the JSON/YAML/table payload, so existing consumers of stdout are unaffected.
- **D-v0.9-6 — no new generic `--filter` flags in 0.9.0.** The passthrough stays on `posts list`
  and `users list` only. `catalogs entries` was planned but dropped: its request DTO has no
  long-tail scalar fields, so the flag would silently forward nothing. Groups/hashtags/attachments
  have no API escape hatch. Rule for the future: add a `--filter` passthrough only when the DTO
  actually has fields the dedicated flags don't cover.
- **D-v0.9-7 — `--filter` value coercion is additive.** `true`/`false` → bool and integer
  literals → int; anything else stays str. A DTO that expects a string where an int-looking
  token is given is a pre-existing edge case: use the dedicated typed flag.
- **D-v0.9-8 — `--validate` costs exactly one extra GET** (post-definition) and only when field
  filters are present; otherwise it is a no-op.

## 5. Open questions

- **Q-v0.9-1 — feature roster (RESOLVED 2026-09-11).** Features 2–13 promoted from the gap census
  (groups A–D above). Excluded from the roster and left as future items: users `order_by`
  allow-list (blocked on an official `orderTypeId` value set, Q-v0.8-2), Q-v0.7-4 field-type →
  filter-type mapping (needs an observed payload), `posts community-list` filter surface
  (medium, requires DTO wiring), `--with-attachment-links` convenience flag, `--max-items` cap.
- **Q-v0.9-2 — client-side validation of screen filters (RESOLVED).** Default stays passthrough;
  validation is opt-in via `posts list --validate` (Feature 5), covering both `--field-filter`
  and `--screen-field-filter` with one post-definition lookup.

## 6. Out of scope

- New endpoint groups — the read inventory is complete through 0.8.0.
- Any write/mutation surface.
- Changes to the posts API layer for Feature 1 (already supports `screen_field_filters`).
- API-layer changes of any kind (all features are CLI/docs only).
- `**filters` passthrough for groups/hashtags/attachments API methods (D-v0.9-6).
