## 1. Objective

A security review of the entire `src/` tree, performed on 2026-09-11 against v0.9.0 (`473c476`),
found **no HIGH-severity vulnerability**, but confirmed two concrete defects in the token-handling
path. This release fixes both.

**Finding A (Medium)** — `HttpTransport.request` redacts the request side but not the response side.
With `audit=True, audit_bodies=True`, the service-account and Google token-exchange responses
(`{"accessToken": "<JWT>"}`) reach every `ClientHooks.on_response` implementation and the
`pynteracta.audit` structlog event in plain text. The hooks channel cannot be mitigated by any
logging configuration; the log channel is scrubbed only when the consumer calls
`setup_default_logging()`, which the library deliberately never does on their behalf. This breaks
the guarantee stated in `docs/logging.md:75` ("neither channel ever receives a raw token"), and
`audit_log_bodies` is not documented as an unsafe opt-in the way `audit_log_raw` is — so enabling
it is not informed consent to token exposure.

**Finding B (Low)** — the token-cache key identifies the credential, never the tenant:
`str(key.client_id)` for service accounts, `profile_name or "default"` for Google. All profiles
share one cache directory by default, the cached JSON carries no tenant marker, and `load()`
validates nothing. Two profiles targeting different tenants whose keys share a `client_id`
(vendor-assigned small integers; certification tenants are often production clones) therefore share
one cache file, and a live production bearer token can be transmitted to a staging host.

Targets a **patch bump 0.9.2 → 0.9.3**: both changes are `fix:` commits with no `feat:`, so
`python-semantic-release` computes a patch (see **D-v0.9.3-1**). No public signature changes; the
only observable differences are redacted response payloads on the two observation channels and a
one-time re-authentication after the cache-key change (**D-v0.9.3-5**).

No endpoints. This release touches `src/pynteracta/transport.py`, `src/pynteracta/hooks.py`,
`src/pynteracta/logging.py`, `src/pynteracta/auth.py`, `src/pynteracta/client.py`,

## 3. Deliverables

### Fix 1 — redact the response side inside the transport (Finding A)

- **`transport.py`** — compute redacted response values immediately after the request returns,
  before either consumer sees them:

  ```python
  redacted_resp_headers = redact_headers(response.headers)
  redacted_resp_body = redact_body(resp_body) if resp_body is not None else None
  ```

  Use `redacted_resp_headers` in place of `dict(response.headers)` in both the `ResponseInfo`
  constructor (`transport.py:159`) and the `audit.response` event (`transport.py:174`), and
  `redacted_resp_body` in place of `resp_body` in both (`:162`, `:177`). Import `redact_body` /
  `redact_headers` are already available in the module (used at `:114-116`).
- **`transport.py` — truncated bodies.** `_capture_response_body` (`:212-221`) returns a **string**
  when the payload exceeds `_AUDIT_BODY_MAX_BYTES`, and a `str` falls through `redact_body` to
  `redact_string`, which only scrubs JWT-shaped substrings. That is correct for Interacta tokens
  but not for Google `ya29.` tokens; the key-regex widening in Fix 1b covers the dict path, and the
  truncated-string path is accepted as-is (**D-v0.9.3-4**).
- **`hooks.py`** — change the `ResponseInfo` docstring (`:27`) to
  `"""Snapshot of a received HTTP response (after redaction)."""`, matching `RequestInfo` (`:17`).
- **Fix 1b — `logging.py`** — widen `_SENSITIVE_KEY_RE` (`:27`) to
  `r"(?i)token|password|secret|privatekey|assertion|jwt"`. `accesstoken` already matches the
  existing `token` alternative; `assertion` and `jwt` close the gap for Google `ya29.` values and
  for any future key that does not contain the substring `token`.
- **Tests (`tests/unit/test_transport.py`, `tests/unit/test_logging.py`)**
  - A respx-mocked auth response `{"accessToken": "eyJ…"}` driven through a transport with
    `audit=True, audit_bodies=True` and a capturing hook asserts `accessToken == "***REDACTED***"`
    in `ResponseInfo.body` — **without** `setup_default_logging()` having been called. This is the
    regression test for the hooks channel, which no logging configuration can mitigate.
  - The same call, with structlog captured via `structlog.testing.capture_logs()` and **no**
    `redaction_processor` installed, asserts the `audit.response` event carries no raw JWT.
  - Response headers containing a JWT-shaped value and a `Set-Cookie` are redacted in both channels.
  - A non-auth response body (ordinary post/user payload) is unchanged by redaction — guards
    against over-redaction of legitimate fields.
  - `redact_body` on `{"assertion": …}` and `{"googleOAuth2Token": "ya29.…"}` returns the marker.
  - An oversized (truncated-string) response body still round-trips through the redaction call
    without raising.
- **Docs** — `docs/logging.md`: keep the §Redaction guarantees wording (it becomes true rather than
  aspirational) and add one sentence stating that redaction happens **in the transport**, so hooks
  and any structlog configuration both receive redacted values. Add a short note under §Hooks (or
  `docs/api/` hooks reference, wherever `ClientHooks` is documented) that `ResponseInfo.body` is
  redacted and that `--audit-raw` does **not** bypass transport-level redaction (**D-v0.9.3-3**).

### Fix 2 — tenant-scoped token-cache key (Finding B)

- **`auth.py`** — add a module-level helper:

  ```python
  def build_cache_key(api_base: str, identity: str) -> str:
      """Namespace a token-cache key by tenant so two tenants never share a file."""
      digest = hashlib.sha256(api_base.encode("utf-8")).hexdigest()[:16]
      return f"{digest}-{identity}"
  ```

  `TokenManager.__init__` sets `self._profile = build_cache_key(transport.base_url,
  str(key.client_id))` in place of the bare `str(key.client_id)` (`:299`).
  `GoogleOAuth2TokenManager` applies the same wrapping to its `cache_key` argument.
- **`transport.py`** — expose the already-stored base as a read-only `base_url` property if it is
  not public yet, so the managers can derive the key without reaching into `_base_url`.
- **`auth.py` — defence in depth.** `FileTokenCache.save` additionally persists `"api_base"`
  alongside the three existing fields (`:253-257`), and `load` discards the entry (returning `None`,
  logging `auth.token_cache_tenant_mismatch` at WARNING) when a stored `api_base` is present and
  differs from the caller's. A cache file written by ≤ 0.9.1 has no `api_base` key; treat its
  absence as "no assertion" and accept the entry, so the change is not a hard break
  (**D-v0.9.3-5**). This requires `load`/`save` to receive the expected base — pass it to
  `FileTokenCache.__init__` (optional, defaulting to `None` = no checking) rather than widening the
  `TokenCache` protocol, so `MemoryTokenCache` is unaffected.
- **`cli/auth.py`** — `logout` (`:283-297`) must compute the identical key, otherwise the command
  silently clears nothing. Derive `api_base` there with `build_api_base(profile_obj.base_url,
  profile_obj.base_path, profile_obj.api_version)` and wrap `key_id` in `build_cache_key`.
- **Tests (`tests/unit/test_auth.py`, `tests/unit/test_cli_auth.py`)**
  - Two `TokenManager`s with the same `client_id` but different transport bases resolve to
    different cache keys, and a token saved by one is **not** returned to the other.
  - The same, for `GoogleOAuth2TokenManager` with `cache_key=None` (the `"default"` path) across two
    bases — this is the library-only variant the CLI never hits.
  - `cli auth logout` clears the file that a preceding `auth login` created (round-trip through the
    real `FileTokenCache`), proving the two derivations stay in sync.
  - A legacy cache file with no `api_base` key is still accepted (no hard break on upgrade).
  - A cache file whose stored `api_base` differs is rejected and triggers a refresh.
- **Docs** — `docs/authentication.md`: document the on-disk file name as
  `<sha256(api_base)[:16]>-<client_id>.token.json`, and add an upgrade note that v0.9.3 causes one
  extra authentication per profile because pre-0.9.3 cache files no longer match.

## 4. Resolved decisions

- **D-v0.9.3-1 — patch, not minor.** Both changes are `fix:` commits with no new public surface, so
  semantic-release computes `0.9.2 → 0.9.3`. The behaviour change (redacted response bodies on the
  hooks channel) is a security correction, not a feature, and matches the documented contract that
  was already published.
- **D-v0.9.3-2 — redact in the transport, not in the log processor.** `redaction_processor` covers
  only structlog and only when the consumer installs it; the hooks channel is entirely independent
  of logging. Putting the redaction in `HttpTransport.request` makes "the transport never emits a
  raw token" a property of the library rather than of the consumer's configuration. This mirrors
  what the request side already does at `transport.py:114-116`.
- **D-v0.9.3-3 — `--audit-raw` no longer bypasses response redaction.** After this change the flag
  disables the structlog redaction processor but the transport has already redacted the values, so
  raw response tokens are no longer reachable through it. This is a deliberate narrowing of an
  explicitly unsafe debugging flag; the documented warning stays, and the docs gain one sentence
  saying what the flag still does and does not expose. Restoring a genuine raw-capture path (for
  example a separate `audit_raw_bodies` transport switch) is out of scope and is **not** planned.
- **D-v0.9.3-4 — truncated bodies keep JWT-shape-only scrubbing.** When a response exceeds
  `_AUDIT_BODY_MAX_BYTES`, `_capture_response_body` returns a string; `redact_body` then reduces to
  `redact_string`, which catches `eyJ…` but not `ya29.…`. Auth responses are far below the cap, so
  the gap is not reachable for the tokens this release is about. Parsing a truncated payload to
  re-apply key-based redaction is not worth the complexity.
- **D-v0.9.3-5 — cache-key change is a silent one-time re-auth, not a migration.** Old
  `{client_id}.token.json` files simply stop matching; the next call authenticates again and writes
  the new name. No migration code, no cleanup of the stale files (they are already `0o600` and
  expire on their own). The `api_base` field added to the payload is advisory: absent means "written
  by an older version, accept it", so downgrading to 0.9.1 also keeps working.
- **D-v0.9.3-6 — informational review items are deferred.** `ServiceAccountKey.__repr__`
  (`auth.py:136-142`), the `0644` audit file created by `RotatingFileHandler` (`logging.py:147`),
  the duplicate `setup_default_logging()` call (`cli/__init__.py:187` + `_common.py:180`) and
  `client_uid` URL-quoting (`api/posts.py:459`) are hardening, not vulnerabilities. Keeping this
  release to exactly the two confirmed findings keeps the security fix reviewable; the four items
  are recorded in §5 as follow-ups.
- **D-v0.9.3-7 — no change to the `TokenCache` protocol.** Tenant checking is a `FileTokenCache`
  concern. `MemoryTokenCache` is per-process and already isolated, so widening the protocol would
  force a no-op implementation on every custom cache.

## 5. Open questions

- **Q-v0.9.3-1 — should `audit_bodies` remain enabled for the two auth transports at all?** An
  alternative to redacting is to construct `auth_transport` and `google_exchange_transport` with
  `audit_bodies=False` (`client.py:106-119`), so auth payloads are never captured. Redaction is
  chosen here because it also protects any *future* endpoint that returns a secret, and because
  silently dropping auth bodies would make the audit trail misleading. Revisit if the redacted
  auth events turn out to have no diagnostic value.
- **Q-v0.9.3-2 — is a deny-list the right long-term shape for `_SENSITIVE_KEY_RE`?** The current
  approach redacts keys matching a pattern. An allow-list (redact everything in an auth response
  except a known-safe set) would be stricter but needs a per-endpoint notion of "safe". Deferred
  until there is a second endpoint family returning secrets.
- **Q-v0.9.3-3 — do any downstream consumers depend on raw `ResponseInfo.body`?** The project has
  no known external hook implementations, and the type is documented as an observation snapshot.
  If one surfaces, the answer is a separate explicit opt-in, never a default.

## 6. Out of scope

- Any API-layer change, any new CLI flag, any new endpoint group.
- The four informational hardening items from the review (**D-v0.9.3-6**), which remain follow-ups:
  `field(repr=False)` on `ServiceAccountKey.private_key_pem`; `os.open(..., 0o600)` for the audit
  file handler; de-duplicating the `setup_default_logging()` call in the CLI; `urllib.parse.quote`
  on `client_uid`.
- Migration or cleanup tooling for pre-0.9.3 token-cache files (**D-v0.9.3-5**).
- Restoring a raw response-capture path to replace what `--audit-raw` loses (**D-v0.9.3-3**).
- Rotating or revoking any token that may already have been exposed through the pre-0.9.3 audit
  path — an operational matter for deployments that enabled `audit_log_bodies`, not a code change.
  Worth calling out in the release notes.
