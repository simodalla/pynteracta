# pynteracta — Roadmap

> **Living index of versions and specs.** This file is the entry point for "where is the project
> going". It is updated in place as plans evolve.
>
> - **Specs** live under [`specs/`](specs/) — since 2026-10-08 one folder per spec
>   (`specs/<nn>-<nome>/`, written with `/sddpa:specifica`, see `CLAUDE.md` "Metodo"); the
>   per-version specs written before that are frozen in [`specs/legacy/`](specs/legacy/).
> - **Build log** (what was actually done, decisions taken, follow-ups) lives in
>   [`PROGRESS.md`](PROGRESS.md) — append-only.
> - **User-facing changelog** is generated by `git-cliff` into [`CHANGELOG.md`](CHANGELOG.md).

## How we work

1. Define the next version's scope with `/sddpa:specifica <ambito>`, which writes
   `specs/<nn>-<nome>/spec.md` (endpoints, deliverables, acceptance criteria, open questions).
2. Add a row to the table below and link the spec.
3. Implement on a dedicated branch (see the **STOP** section in [`CLAUDE.md`](CLAUDE.md)).
4. Log the outcome in `PROGRESS.md`; let semantic-release cut the tag and `git-cliff` the changelog.
5. Mark the version ✅ here and freeze its spec.

## Versioning policy

Pre-1.0 (current): every feature is a **minor** bump, and even breaking changes bump the minor
(lenient pre-1.0 convention). `python-semantic-release` is configured with
`allow_zero_version = true` and `major_on_zero = false`. A strict-semver 1.0 is deferred until
the read surface is complete and the API has been stable for a while. **PyPI publication is not
gated on 1.0** (decided 2026-09-12, see [specs/legacy/v0.9.4-pypi-publication.md](specs/legacy/v0.9.4-pypi-publication.md)):
releases are published to [PyPI](https://pypi.org/project/pynteracta/) from v0.9.4 onward, and
`Development Status :: 3 - Alpha` carries the stability signal.

**Scope cadence:** one read-endpoint group per minor release (decided 2026-06-04).

## Write surface (in scope since 2026-10-08, [ADR 0001](specs/adr/0001-apertura-della-superficie-di-scrittura.md))

The 34 mutating endpoints of the pinned swagger, plus the read "form-prep" helpers that are
propaedeutic to them. One spec per group (order decided spec by spec, see `specs/prd.md`
RF-021…RF-025):

- **Posts & comments** (15) — `communication/posts/manage/*`: create/edit post and event-post,
  custom data, attachments, watchers, workflow screen data and operations, copy, delete,
  mark-as-erasable, event participation, create-comment; helpers `post-data-for-create|edit|copy`,
  `event-post-data-for-*`, `post-workflow-screen-data-for-edit`.
- **Tasks** (3) — `communication/tasks/manage/*`: create, edit, delete.
- **Admin** (15) — `admin/manage/*`: users (create, edit, delete, credentials), groups (create,
  edit, delete, members), catalogs and entries (create, edit, `deleted` flag), workspace edit.
- **Attachment upload** (1) — `core/storage/upload-new-attachment`.

## Deferred / future

- **Async client** (`AsyncInteractaClient`).
- **Alternate auth**: Microsoft OAuth2, username/password (same exchange pattern as Google OAuth2).
- **Automatic retry/backoff** with jitter — **reads only**: writes are never retried automatically
  (non-negotiable rule, ADR 0001).
- **Strict-semver 1.0** once the surface is stable. (PyPI publication shipped in 0.9.4.)
