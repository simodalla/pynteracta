# pynteracta — Roadmap

> **Living index of versions and specs.** This file is the entry point for "where is the project
> going". It is updated in place as plans evolve.
>
> - **Per-version specs** live under [`specs/`](specs/) — one file per version, written *before*
>   the work starts, frozen once shipped.
> - **Build log** (what was actually done, decisions taken, follow-ups) lives in
>   [`PROGRESS.md`](PROGRESS.md) — append-only.
> - **User-facing changelog** is generated by `git-cliff` into [`CHANGELOG.md`](CHANGELOG.md).

## How we work

1. Define the next version's scope in a new `specs/vX.Y-<slug>.md` (copy the shape of an existing
   spec: endpoints, deliverables, acceptance criteria, open questions).
2. Add a row to the table below and link the spec.
3. Implement on a dedicated branch (see the **STOP** section in [`CLAUDE.md`](CLAUDE.md)).
4. Log the outcome in `PROGRESS.md`; let semantic-release cut the tag and `git-cliff` the changelog.
5. Mark the version ✅ here and freeze its spec.

## Versioning policy

Pre-1.0 (current): every feature is a **minor** bump, and even breaking changes bump the minor
(lenient pre-1.0 convention). `python-semantic-release` is configured with
`allow_zero_version = true` and `major_on_zero = false`. PyPI publication and a strict-semver
1.0 are deferred until the read surface is complete and the API has been stable for a while.

**Scope cadence:** one read-endpoint group per minor release (decided 2026-06-04).

## Read-surface inventory (target for the 0.2–0.6 line)

Endpoints present in the pinned swagger but **not yet covered**, grouped by the minor that will
add them. (`✅` = already shipped in 0.1.0, listed for context.)

### 0.2.0 — Posts read completeness (M15)
- `GET  communication/posts/data/post-detail-by-client-uid/{clientUid}` → `GetPostDetailResponseDTO`
- `GET  communication/posts/data/post-capabilities/{postId}` → `GetPostCapabilitiesResponseDTO`
- `POST communication/posts/data/history-list/{postId}` → `ListPostHistoryEventsResponseDTO`
- `POST communication/posts/data/global-stream` → `GlobalPostsStreamResponseDTO`
- `POST communication/posts/data/community-list/{communityId}` → `PagedListPostsResponseDTO` (distinct from the existing `list/community/{communityId}`)
- `POST communication/posts/data/check-visibility` → `CheckVisibilityWithCommentsResponseDTO`
- `POST communication/posts/data/check-visibility-with-comments` → `CheckVisibilityWithCommentsResponseDTO`

## Deferred / future (post read-completion)

- **Write operations** — the 10 mutating endpoints, plus the read "form-prep" helpers
  (`post-data-for-create/edit/copy`, `event-post-data-for-*`, `post-workflow-screen-data-for-edit`)
  which are propaedeutic to writes and were intentionally excluded from the read line.
- **Async client** (`AsyncInteractaClient`).
- **Alternate auth**: Microsoft OAuth2, username/password (same exchange pattern as Google OAuth2).
- **Automatic retry/backoff** with jitter.
- **PyPI publication + strict-semver 1.0** once the surface is stable.
